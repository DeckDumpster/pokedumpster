 SeaweedFS IAM Policy Enforcement Issue #8516

 Copy link 

 Description
 
 SrikanthBhandary 
 opened on Mar 5, 2026 

 Issue body actions 

 Summary

 IAM policies are successfully created and attached to users, but S3 operations performed with those user credentials consistently fail with AccessDenied errors, even after significant wait times for policy propagation.

 Environment

 SeaweedFS Version : 4.14 ( 7799804 linux arm64)

 Deployment : Kubernetes cluster
 
 2 Filer pods

 3 Master pods

 3 Volume pods

 Client : AWS SDK for Go v2 and AWS CLI v2

 Endpoints :
 
 Filer: http://localhost:8888 

 S3/IAM: http://localhost:8333 

 Steps to Reproduce

 1. Create IAM User via AWS CLI

 aws iam create-user --user-name cli-test-user \
 --endpoint-url http://localhost:8333 

 2. Create Access Keys

 aws iam create-access-key --user-name cli-test-user \
 --endpoint-url http://localhost:8333 

 Response: 

 {
 "AccessKey" : {
 "AccessKeyId" : " AKIAXXBGMITYZ11E3R11 " ,
 "SecretAccessKey" : " td49fYrjTJN54AOyEjNcUjSjFUCyEdMrXVqoVZHO " ,
 "Status" : " Active " ,
 "UserName" : " cli-test-user " 
 }
} 

 3. Create S3 Bucket

 aws s3api create-bucket --bucket cli-test-bucket \
 --endpoint-url http://localhost:8333 

 4. Create IAM Policy

 aws iam create-policy --policy-name cli-test-policy \
 --policy-document ' { 
 "Version": "2012-10-17", 
 "Statement": [{ 
 "Effect": "Allow", 
 "Action": [ 
 "s3:PutObject", 
 "s3:GetObject", 
 "s3:DeleteObject", 
 "s3:ListBucket" 
 ], 
 "Resource": [ 
 "arn:aws:s3:::cli-test-bucket/*", 
 "arn:aws:s3:::cli-test-bucket" 
 ] 
 }] 
 } ' \
 --endpoint-url http://localhost:8333 

 5. Attach Policy to User

 aws iam attach-user-policy \
 --user-name cli-test-user \
 --policy-arn arn:aws:iam:::policy/cli-test-policy \
 --endpoint-url http://localhost:8333 

 6. Verify Policy is Stored and Attached

 Check Policy Document: 

 curl -s http://localhost:8888/etc/iam/policies/cli-test-policy.json 

 Response: 

 {
 "Version" : " 2012-10-17 " ,
 "Statement" : [
 {
 "Effect" : " Allow " ,
 "Action" : [
 " s3:PutObject " ,
 " s3:GetObject " ,
 " s3:DeleteObject " ,
 " s3:ListBucket " 
 ],
 "Resource" : [
 " arn:aws:s3:::cli-test-bucket/* " ,
 " arn:aws:s3:::cli-test-bucket " 
 ],
 "NotResource" : null 
 }
 ]
} 

 Check User Identity: 

 curl -s http://localhost:8888/etc/iam/identities/cli-test-user.json 

 Response: 

 {
 "name" : " cli-test-user " ,
 "credentials" : [
 {
 "access_key" : " AKIAXXBGMITYZ11E3R11 " ,
 "secret_key" : " td49fYrjTJN54AOyEjNcUjSjFUCyEdMrXVqoVZHO " ,
 "status" : " Active " 
 }
 ],
 "policy_names" : [
 " cli-test-policy " 
 ]
} 

 ✅ Verification Result : Policy document is correctly stored, and policy name is correctly listed in user's policy_names array.

 7. Attempt S3 Upload with AWS CLI

 Configure AWS CLI: 

 aws configure set aws_access_key_id AKIAXXBGMITYZ11E3R11 --profile seaweed-test
aws configure set aws_secret_access_key td49fYrjTJN54AOyEjNcUjSjFUCyEdMrXVqoVZHO --profile seaweed-test
aws configure set region us-east-1 --profile seaweed-test 

 Attempt Upload (Immediately): 

 echo " This is a test file from AWS CLI " > /tmp/test-file.txt
aws s3 cp /tmp/test-file.txt s3://cli-test-bucket/test-file.txt \
 --endpoint-url http://localhost:8333 \
 --profile seaweed-test 

 Result: 

 upload failed: ../../../../../tmp/test-file.txt to s3://cli-test-bucket/test-file.txt An error occurred (AccessDenied) when calling the PutObject operation: Access Denied.

 Attempt Upload (After 5 second delay): 

 sleep 5
aws s3 cp /tmp/test-file.txt s3://cli-test-bucket/test-file.txt \
 --endpoint-url http://localhost:8333 \
 --profile seaweed-test 

 Result: 

 upload failed: ../../../../../tmp/test-file.txt to s3://cli-test-bucket/test-file.txt An error occurred (AccessDenied) when calling the PutObject operation: Access Denied.

 Expected Behavior

 After attaching a policy with s3:PutObject permission to a user, S3 operations using that user's credentials should succeed for the specified resource.

 Actual Behavior

 S3 operations consistently fail with AccessDenied error, even though:

 ✅ Policy document is correctly stored in /etc/iam/policies/ 

 ✅ Policy grants s3:PutObject permission

 ✅ Policy is listed in user's policy_names array

 ✅ Resource ARN matches: arn:aws:s3:::cli-test-bucket/* 

 ✅ User credentials are valid (Active status)

 ✅ Bucket exists and was created successfully

 Additional Testing

 Test with AWS SDK for Go v2

 The same issue occurs when using AWS SDK for Go v2:

 // Configure S3 client with user credentials 
 awsCfg , _ := config . LoadDefaultConfig ( ctx ,
 config . WithRegion ( "us-east-1" ),
 config . WithCredentialsProvider ( credentials . NewStaticCredentialsProvider (
 "AKIAXXBGMITYZ11E3R11" ,
 "td49fYrjTJN54AOyEjNcUjSjFUCyEdMrXVqoVZHO" ,
 "" ,
 )),
)

 s3Client := s3 . NewFromConfig ( awsCfg , func ( o * s3. Options ) {
 o . BaseEndpoint = aws . String ( "http://localhost:8333" )
 o . UsePathStyle = true 
})

 // Attempt to upload 
 _ , err := s3Client . PutObject ( ctx , & s3. PutObjectInput {
 Bucket : aws . String ( "cli-test-bucket" ),
 Key : aws . String ( "test.txt" ),
 Body : strings . NewReader ( "test content" ),
})

 // Result: AccessDenied error 

 Retry Logic Testing

 Implemented exponential backoff with 5 retry attempts over 20+ seconds:

 Attempt 1: Immediate → AccessDenied

 Attempt 2: After 2s → AccessDenied

 Attempt 3: After 4s → AccessDenied

 Attempt 4: After 6s → AccessDenied

 Attempt 5: After 8s → AccessDenied

 Total wait time: 20+ seconds, still fails.

 Analysis

 The IAM policy attachment API works correctly at the metadata level:

 Policy documents are stored in the filer

 User-policy associations are recorded in user identity files

 IAM API operations (CreateUser, CreateAccessKey, CreatePolicy, AttachUserPolicy) all succeed

 However, the S3 service does not enforce these policies when validating user credentials for S3 operations. This suggests a disconnect between the IAM metadata storage and the S3 request authorization logic.

 Related Information

 Tested with AWS CLI v2 and AWS SDK for Go v2

 Both produce identical AccessDenied errors

 Admin credentials (not subject to IAM policies) work fine for S3 operations

 Questions

 Is there additional configuration required for IAM policy enforcement?

 Are there SeaweedFS logs that would show policy evaluation attempts?

 Is this feature still under development or experimental?

 Should policies be stored in a different location or format?

 Impact

 This issue prevents using SeaweedFS as an AWS S3-compatible service with proper IAM access control, which is critical for multi-tenant and security-conscious deployments.
