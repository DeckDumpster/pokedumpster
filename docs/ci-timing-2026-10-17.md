# Where pokedumpster CI time goes (measured 2026-10-17, sp-n1bfe4)

Measurement only. The one code change is per-step timestamps in `deploy/ci.sh` (see §8).

## 1. Method and sample

* **Source**: the last 38 completed `CI` runs of `ci.yml` on `DeckDumpster/pokedumpster`
  (run numbers 381–420, 2026-10-15 23:19Z → 2026-10-17 04:34Z), pulled through the Actions REST API:
  per-job step timings, plus each `gate` job's raw log, whose lines carry GitHub's per-line timestamps.
  3 cancelled runs excluded (they never started `ci.sh`).
* A **step's duration** is the time from its `==> <name>` line (the `step "…"` calls in `ci.sh`) to the next one.
  The queued container gates print their output buffered per gate when they finish (`ci-parallel.sh`), so
  inside the parallel phase the only trustworthy numbers are the per-gate `ok  <gate>  <N>s` lines
  `ci-parallel.sh` prints at the end; those are used.
* Playwright per-spec numbers are summed from the `list` reporter's per-test `(NNNms)` lines.
* **Statistics are over the 19 full, green runs** (all tiers, ≥14 queued gates): runs 382, 383, 389, 392, 394,
  395, 396, 400, 402, 403, 405, 406, 407, 413, 414, 416, 418, 419, 420. Run 412 was a partial-tier run (docs-
  selected tiers) and the 17 red runs are reported separately (§6). p90 on n=19 is the 18th value.
* The runner is an ephemeral 8-core / 15.3 GiB EC2 VM (`runner-deps: machine x86_64: 8 cores, 15.3 GiB RAM`),
  cold: no warm cargo target, no image layer cache, no node_modules.
* Raw per-run data is not committed; the table in §2 is the per-run record. Shares below are of the median
  `gate` job (1636 s). Median whole workflow, including VM provision/teardown, is 1796 s (p90 2243 s).

**The trend matters more than the median**: runs 382–407 took 1358–1689 s; runs 413–420 took 1672 → 2143 s
(gate job). Over runs 414 → 420 the image build went 253 → 615 s and `cargo test` 243 → 334 s. The image
growth lines up with `sp-4k7mxi.4/.5` and `sp-vxa4l8` (adf2da8), which added the Rust lake binaries
(`pkdump-lake-*`, `pkdump-lakejobs`) to the image; that is a correlation read from `git log`, not a measured
attribution.

### What overlaps and what is serial

Strictly serial today, in this order: lint self-tests (47) → fmt → **cargo test (244) → clippy (40)** → store gates
(37) → frontend (18) → **image build (252)** → start instance (12) → **browser (129)** → queue → **16 gates at cap 2
(749)**. Only the queued gates overlap (two at a time). Nothing in the first block depends on anything before
it except the tree: **the image build needs only the source tree**, not `cargo test`, clippy or the frontend
step, and could start at t=0. The browser tier needs the image and the running instance only.

## 4. (a) Double builds

"Never double builds" — what is built more than once per run, from the run-420 log:

| what | where | cost (run 420) | note |
|---|---|---|---|
| Rust workspace, **debug/test profile** | `cargo test` | 3 m 09 s compile (`Finished test profile … in 3m 09s`), 334 s step | cold: fresh VM, no target dir |
| Rust workspace, **check profile** | `cargo clippy` | 50 s | reuses nothing from the test build's codegen |
| Rust workspace, **release profile** | `podman build` builder stage | **9 m 26 s** (`Finished release … in 9m 26s`) | whole image step 615 s; deps recompiled from zero (`the cargo target cache was written from other sources — restamping mtimes`) |
| Rust, debug again, in the gates | `cargo build --bin pkdump` in `recreate.sh`/`drill.sh`; `cargo build -p pkdump-server --example access_fixture` in `tenants/handles.sh` | 37 s / 7 s / 1.1 s / 0.2 s (`Finished test profile` lines in gate output) | different artefact than `cargo test` produced, so it recompiles; occupies a gate slot |
| **Frontend** (`vite build`) | `ci.sh` "Frontend" step **and** the image's node stage | ≈ 2.5 s + ≈ 10 s (`vite … building client environment` at 04:07:40 and again 04:17:44) | tiny in seconds, but the same build twice |
| Lake job image (`lake/Containerfile`, PyIceberg) | `lake/run.sh`, `prices.sh`, `value_snapshots.sh`, `phase3.sh` each run `podman build` | not separately timed; first build is real, later ones depend on layer cache and on whether they run concurrently with the first | `ci.sh` builds the app image once and shares it via `PKDUMP_PREBUILT_IMAGE`; the lake image has no such share |

The app image itself **is** built once (`PKDUMP_PREBUILT_IMAGE`; `setup.sh` ×3 and the five image-needing gates
all print `Tagging … (built once this run)`). The real doubling is the Rust compile three ways (test, clippy,
release) plus the frontend twice. The release compile is the single largest serial block in the run.

## 5. (b) The UI step: fixtures, server, sharding

This is the **browser tier** (`tests/visual`, Playwright); the intents harness `tests/ui` is deliberately not in CI.

* **Server and fixture.** One `--test` container instance (`pkdump-ci-<hash>`), seeded by `setup.sh --test` from
  the committed `tests/ui/fixtures/{shared,collection}.sqlite`, started once in `ci.sh` and shared with the
  browser tier (`PKDUMP_BASE_URL=http://localhost:<port>`). The same instance is used by nothing else in CI —
  each queued gate builds its own instance — so the browser tier does not contend with the gates.
* **Concurrency today.** `playwright.config.ts`: `fullyParallel: false`, `workers: 1`, two projects
  (`desktop-1440`, `mobile-768`) running one after the other in a single worker. The config's stated reason:
  "a shared server instance: serialise, so nothing races on the fixture".
* **Does anything write?** A grep of the six specs finds no POST/PUT/DELETE/PATCH and no request-context writes;
  the only interactions are `.click()`s on client-side controls (burger menu, "Select" mode, column drawer,
  rarity sort, collapse). The specs are GET-only against the server as far as that read can show. **I did not
  verify that those clicks cause no server write** (e.g. persisted view preferences) — that is the thing to
  check before sharding.
* **Time.** 100 tests, 1.9 min of tests (108 s summed per-test) inside a 129 s step; ≈ 20 s is `npm ci` +
  Chromium install. Per spec, summed over both projects (median): `routes.spec` 52.5 s (22 tests × 2),
  `collection-window.spec` 39.8 s (17 × 2, with four `waitForTimeout(250)` waits), `browse-footer.spec` 10.1 s,
  `browse-mobile` 2.6 s, `collection-mobile` 2.1 s, `collection-toolbar` 0.8 s. Per project they are almost
  exactly equal (desktop 54 s / mobile 54 s).
* **Sharding verdict.** Sharding is safe only with an isolated server + fixture DB per shard *or* with
  read-only specs against one server. The present specs look read-only, so `workers: N` / one worker per
  project against the **one** instance is plausible; the safe variant, a second instance per shard, costs a
  second `setup.sh --test` (≈ 12 s) and is what any future spec that writes will need.
  Red-run behaviour: the browser tier failed in 7 of 17 red runs, three of those at ~330 s and one at 1219 s
  (a hang to timeout), always *after* the ~10 min of build/test that precede it.

## 6. Where red runs spend their time

17 of the 36 non-cancelled runs were red: 13,271 s of gate-job time (30% of all gate-job time in the window).
Failure points (last step reached): browser tier 7, "Key custody" queueing 5, frontend 3, use-case gate 1, fmt 1.
A red browser run has already spent ≈ 20 min on cargo test + image before the 2 min browser tier can fail.

## 7. Ranked reductions

Savings are against the recent (run 414–420) steady state, in wall seconds per green run. "Measured" means the
number is read off the logs above; "estimated" means it is a projection I did not run.

| # | reduction | est. saving | risk |
|---|---|---|---|
| 1 | **Warm the Rust compile on the VM template** (bake `CARGO_HOME` + a deps-only `target/` + the builder image layers into the ephemeral-ci template, as `ci.yml`'s header already proposes). The cold deps compile is most of both the 9 m 26 s release build and the 3 m 09 s test build. | est. 300–500 s (release build is 615 s of step today; the workspace-only share is unmeasured — instrument first) | medium: template maintenance and staleness; `pd-sjn7`/`pd-wjmd` cache-stamp logic must still hold |
| 2 | **Start the image build at t=0, in the background**, and join it where the image is first needed. It depends on the source tree only, not on cargo test/clippy/frontend. Also lets the browser tier run at ≈ t+8 min instead of ≈ t+20 min on red runs. | est. 150–250 s (8 cores shared, so less than the full 252–615 s overlap); red browser runs fail ≈ 10 min sooner | medium: CPU contention between two compiles; the treewatch/`step()` bookkeeping must tolerate a background job |
| 3 | **Raise the queued-gate cap from 2 to 4** (8 cores, 15 GiB, one run per VM — the shared-box reasoning for cap 2 no longer applies). Phase is cap-bound: 1536 s of gate-time / 2 = 768 s observed; at 4 the floor is the 456 s `alarming` pole. | est. 250–300 s | medium: each gate runs 2–3 containers; resource exhaustion presents as flakes (the original reason for the cap). Try 3 first |
| 4 | **Shorten the two poles**: `alarming` (456 s; ~30 `sleep 1` polls) and `schema-version` (400 s; its content is "~1 image build + 2 starts" yet takes 400 s — find what it waits on). Once the cap is raised these two are the floor of the phase. | est. up to 150–200 s after #3 | low–medium: need per-section timing first; the new step timestamps do not reach inside gates |
| 5 | **Shard the browser tier**: `workers: 2` (or one worker per project) against the one instance; specs appear GET-only. | est. 50–60 s | medium: confirm the clicks write nothing server-side; flake risk on `waitForTimeout`/`networkidle` specs |
| 6 | **Fail the red-prone steps earlier**: run the browser tier as soon as the image exists (follows #2), and make the Frontend step a fast-fail ahead of `cargo test`. | est. 600–900 s on the 7/36 runs that die in the browser tier; 0 on green runs | low |
| 7 | **Bake runner deps** (the 81 s `runner-deps.sh` apt/node install) into the template. | est. 60–80 s | low |
| 8 | **Remove the second Rust compile in gates**: build `pkdump` and the example once (or reuse `cargo test`'s artefacts via `cargo test --no-run` + shared `CARGO_TARGET_DIR`) rather than three `cargo build` calls inside gates. | est. 10–30 s of gate-slot time | low |
| 9 | **Build the lake image once in `ci.sh`** and share it like `PKDUMP_PREBUILT_IMAGE`. | est. unmeasured (≤ 1 build's worth × 3); verify with timings first | low |
| 10 | **Drop the host `npm run build`** from the Frontend step (the image builds it again). | ≈ 3–10 s; tests/check stay | low, but confirm `cargo test` does not embed `frontend/build` |
| 11 | Move `tenant_isolation_selftest.sh` (21 s) and the refresh gate (35 s, serial today) into the parallel phase. | est. 30–50 s | low |

Outside our hands: VM provision (136 s median) and teardown (9 s) are the `ephemeral-ci` actions.

Not worth doing: re-ordering the queued gates (≈ 10 s at cap 2) and anything in the ~35 lint self-tests
beyond #11 (47 s total).

## 8. Per-step timestamps now in the log

`deploy/ci.sh` `step()` now prints, under each unchanged `==> <name>` line,
`    [step-time] HH:MM:SSZ t+<N>s` (offset from the run's start), and the run ends with
`==> Step timings (longest first …)` — the 15 slowest steps with their own duration — before `CI passed in …`.
That is the first thing that exists inside a locally run or `ci-parallel.sh`-buffered output, where GitHub's
line timestamps do not. It does not look inside the queued gates; the per-gate `ok <gate> <N>s` summary
remains the only gate-level number, and sub-gate timing (#4) would need the same treatment in the gate scripts.
The next run's log will show the lines; I could not run `ci.sh` here (tests run only through `testenv`), so the
function was exercised in isolation and `tests/ci/treewatch_test.sh` (which inspects `step()`'s body) was run.
