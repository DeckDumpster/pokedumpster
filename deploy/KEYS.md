# Tenant-zone key custody

**The one thing to take away: losing the master key is not the same event as
deleting a tenant, and this system must never report one as the other.**

Crypto-shredding is defence in depth for the tenant zone (`pd-8lw7` item 3).
The zone's real deletion is a partition drop; this is the second lock on the
same door, so that bytes surviving a drop somewhere — an older copy, a backup,
a mistake — are bytes nobody holds a key for.

```
  ~/.config/pkdump/<instance>/tenant-master.key     one master key, mode 600
           │                                          (beside litestream.env)
           │  HKDF-SHA256(salt, master, database_id)
           ▼
  per-tenant key                                    DERIVED, never stored
           ▲
           │  refused when …
  registry.sqlite : tenant_key(database_id -> active | tombstoned)
```

Nothing per-tenant is written down. There is no key service to run, no
per-tenant secret to rotate, and nothing to lose one tenant at a time.

---

## 1. The property this is all arranged around

> A lost key is indistinguishable from a deleted tenant, **by design**.

Cryptographically, yes: ciphertext nobody holds a key for is unreadable, and
*why* nobody holds the key does not change the maths. Operationally it is a
trap, because the two causes call for opposite responses:

| what happened | what it means | what to do |
|---|---|---|
| the key was destroyed on purpose | the system is working | nothing; the account is gone and stays gone |
| the key cannot be found | the system is broken | restore it (§4), and page somebody until you have |

Collapse those into one and the failure is silent in **both** directions:

* a backup failure starts reading as a legitimate deletion — data loss wearing
  compliance as a costume;
* a deletion gets implemented as "the backup went missing", which revokes
  nothing the moment the backup turns up.

So **backup and destruction are deliberately different code paths**, and the
difference is structural rather than nominal:

| | backup (§4) | destruction (§5) |
|---|---|---|
| object | the master key **file** | a row in the key-state **registry** |
| verb | copy it out / put it back | record a tombstone |
| scope | every tenant at once | exactly one `database_id` |
| reach | never opens the registry | never opens the key file |
| code | `crates/pkdump-keys/src/backup.rs` | `crates/pkdump-keys/src/destroy.rs` |

That last row is a rule, not a description.
`crates/pkdump-keys/tests/separation.rs` reads both files and fails if either
grows a reference to the other's world — so it stays true of code nobody has
written yet.

**In the code**, `KeyError::is_deliberate_revocation()` answers `true` for one
variant and one variant only. Ask through it. `Err(_) => "deleted"` is one
keystroke away from turning a missing backup into a compliance claim.

## 2. Where the key lives

`~/.config/pkdump/<instance>/tenant-master.key`, mode **600**, in the
directory `deploy/setup.sh` already creates at mode 700 for that instance's
`litestream.env` and `aws/config`.

Per-instance, not per-box, because the key **state** is per-instance — the
tombstones live in that instance's `registry.sqlite`. A master key paired with
the wrong registry is a key that derives happily for a `database_id` somebody
else revoked.

The binary finds it through `$PKDUMP_MASTER_KEY_FILE` (default
`$HOME/.config/pkdump/tenant-master.key`). `deploy/keys.sh <instance>` is the
wrapper that knows which file that is; use it rather than exporting the
variable by hand.

```bash
bash deploy/keys.sh prod status
```

---

## 3. Minting it

Not done by `deploy/setup.sh`, on purpose — the same reason the Litestream
bootstrap key is not: a secret's creation is an operator's decision, and a
key generated by a script nobody was watching is a key nobody backed up.

```bash
bash deploy/keys.sh <instance> init
```

It refuses if a key is already there. **There is no `--force`.** Overwriting
the master key destroys every tenant's derived key at once and there is no
undo; if that is genuinely what you want, move the file aside with your own
hands first.

Record the printed fingerprint. It is a non-invertible 16-hex-character
identifier, safe to keep next to the ticket, and it is how you later confirm
the key in the password manager is the key on the box.

## 4. THE BACKUP PATH

**The mechanism is matched, not invented: the master key is backed up exactly
the way the Litestream bootstrap credential already is — a copy in the
operator's password manager, pasted back by hand in
`deploy/RESTORE.md` Scenario C.**

There is deliberately no automated replication of it. The obvious place to
replicate it to is S3, and S3 is where the data it protects lives. A key
stored beside its ciphertext protects nothing.

```bash
# Print it (this is secret material — --yes is the acknowledgement):
bash deploy/keys.sh <instance> backup --yes

# …or stage a mode-600 copy, move it into the password manager, delete it:
bash deploy/keys.sh <instance> backup -o /run/user/$(id -u)/tenant-master.key
```

Putting it back:

```bash
bash deploy/keys.sh <instance> restore -i /path/to/pasted-key
```

`restore` refuses over a live key, and validates the paste **before** it
becomes the key file — a paste that lost a character fails as a bad paste, not
as a box that silently derives the wrong key for every tenant from now on.
Check the fingerprint it prints against the one from §3.

**A restore does not lift any tombstone.** Revocation lives in the registry,
not in the key. That is the whole reason the two are separate.

## 5. THE DESTRUCTION PATH

```bash
bash deploy/keys.sh <instance> tombstone <database-id> --yes --reason "account deleted"
```

Addressed by `database_id` — as printed by `pkdump tenant list` — never by
handle, because a revocation is not something to reach by typo.

What it does: writes one row saying this `database_id`'s key will not be
derived again. That is the entire act. It does not touch, read, move or even
look for the master key file.

After it:

* derivation for that id refuses, permanently, **whether or not the master key
  is present**;
* every other tenant is unaffected;
* deleting the user row does not undo it (the tombstone has no foreign key,
  deliberately — see `schema_registry.sql`);
* restoring any backup does not undo it;
* `pkdump keys register` on that id refuses. A tombstone is terminal.

**The trade, stated rather than hidden:** a tombstone stops *our code* from
deriving that key. It is not itself an unrecoverable erasure of the master
key's ability to re-derive it — anybody holding the master key and willing to
bypass this registry could. That is exactly why the registry, and not the
master key, is what deletion touches: the alternative, "destroy the key",
revokes *everybody* and is an outage, not a deletion. The actual erasure is
the partition drop; this is the second lock.

**Both locks at once** — which is what an account deletion actually is — are
`bash deploy/erase.sh <instance> delete --tenant <handle|id> --yes`. It calls
this path first and then drops the partition, and it will not report success
until it has attempted every read path and been refused by all of them. See
[`DELETION.md`](DELETION.md). Running the `tombstone` above on its own is
correct and sometimes what you want, but on its own it is not a deletion:
the objects are still there.

## 6. Registering a tenant

```bash
bash deploy/keys.sh <instance> register <database-id>
bash deploy/keys.sh <instance> list
```

**Absence is not permission.** A `database_id` with no row is *refused*, not
derived for. This is fail-closed on purpose: a registry that came back empty
from a restore is missing its tombstones as well as its users, and the
direction where that is loud is the safe one.

If `keys list` is empty on a box you expected rows on — **stop**. Restore the
registry (`deploy/RESTORE.md`, and note the registry is restored *first*)
before doing anything else.

---

## 7. Proving it works, on a real box

```bash
# Determinism: same id, same key, always.
bash deploy/keys.sh <instance> derive <database-id>
bash deploy/keys.sh <instance> derive <database-id>   # identical fingerprint

# Distinctness: a different id is a different key.
bash deploy/keys.sh <instance> derive <other-database-id>   # different fingerprint

# The file really is 600, where it really is deployed:
stat -c '%a %n' ~/.config/pkdump/<instance>/tenant-master.key
```

`derive` prints a **fingerprint**, never the key, so all of this is safe in a
shell history and a CI log.

`tests/keys/run.sh` is the container-tier gate that asserts exactly these,
against the shipped image, including the mode of the deployed file — "the code
sets 600" and "the file is 600" are different claims and only the second one
matters.

## 8. What this is not, and what comes next

**Not built here, deliberately:** the deletion path itself. `pkdump-erase`
(`pd-qbrf`) drops the partition and *calls* §5 rather than reimplementing it —
[`DELETION.md`](DELETION.md).

**A documented future option:** stored per-tenant random keys, rather than
derived ones. They are stronger against a master-key-leak threat model — one
leaked key would stop being every tenant's key. Moving to them costs a
re-encrypt of at most **90 days** of data, because 90 days is the tenant zone's
whole retention window. It is a real option with a bounded price, not a regret,
and it is not this item's work.

**The trade in the current shape, once more:** there is one master key, so
destroying *it* destroys everything. That is why §3 refuses to overwrite, why
§4 exists at all, and why §5 cannot reach the file.
